# 上下文问题


##  关于上下文有哪些处理方案
- llm压缩
- 过滤 ： 
- 占位符替代

压缩的核心是去掉 低价信息，可恢复信息，保留推理路径，重要中间成果和 当前进展 

压缩的主要限制是必须考虑 kv cache的复用，二者本质互相冲突

因此 无论是代码直接处理，还是模型自行处理，本质上都是在做 信息的判断，判断哪些是低价值信息（ 例如工具调用 错误消息， 用户消息始终为高价值信息） ，判断哪些是可恢复信息 （例如就是tool的输出，可以重新执行tool再次获得）

- 初始任务需求未澄清或者由于中间工具输出的误导  导致 跑偏， 这也可以归纳为指令偏移（ 不再遵守系统提示词， 
- 脱离任务边界 ： 这里不同于第二点的是，第二点是朝着错误的方向走了，但是这里是知道正确方向，但还是做了超出我们让他预期的事



web agent, 或者是codeagent , 其面临的问题不是在具体环境下不知道该怎么处理哪一步， 而是在过长的工具输出中（ 搜索的网页内容， 看到的代码文件 符号等） 忘记了自己当前所处哪一步中，当前已经得到什么，离最终的目标的距离，可以称之为 方向感
即  长程 agent 的核心问题，往往不是不会做某一步，而是不知道自己现在走到哪里、下一步该怎么继续推进。

对于第二种，需要一个后台的偏移检测机制 ，这篇文章[读 Meta 论文《Wink: Recovering from Misbehaviors in Coding Agents》](https://zhuanlan.zhihu.com/p/2021574513674952824)






## 怎么评估agent

任务成功率
tool调用准确率
指令遵循程度
智能程度（ 多个方案中，知道哪个最佳，少走弯路） 
复杂场景下的 非打转次数程度


很多 benchmark 本质上仍然是在考 agent 会不会解题，但真实系统更像是在考：
它能不能在复杂环境里稳定地做事。这里的“稳定”不只是平均成功率高，还包括：

少偏航
少乱改
少工具误用
少无效循环
出错后能恢复
必要时知道交还给人

先提升任务的准去率，再去提升智能性
